# 13–15조: 평가·실현·개정

[통합 헌법](../HSWM_CONSTITUTION.md)의 선택 가능한 한 부분이다.
이 문서의 검토 구성은 `agent(codex) / SECONDARY_AI`다.

## 13. 대상·실행·효능을 따로 판정한다

사용자 방향은 만들 대상과 요구를 정한다. 코드·테스트는 구현의 특정 동작을 검사한다.
형식 증명은 선언된 전제와 명제에 한정된다. 독립 효능은 실제 과제와 비교군·예산·관측으로
평가한다. 그래프 조회·SHACL 통과·기록 수·문서 길이가 어느 층도 대신하지 않는다.

HSWM은 별도 프로그램이고 HSWM_LIKENESS는 성질과 근거를 평가한다. 기존
[전체 프로그램 평가 계약](../../../../HSWM_LIKENESS/docs/PROGRAM_ASSURANCE.md)의
8개 축 × 3개 층 = 24개 항목, CR-0…7/FCL-1…8의 16개 의무, 13개 연구 주제,
동일 시스템 통합 근거를 유지한다. 이 문서는 새 점수나 프로파일을 만들지 않는다.
미확인은 미확인으로, 과거 무개선·하락·중단은 해당 범위의 결과로 남긴다.

OpenCog Hyperon은 기존 사용자 지시에 따른 핵심 비교 대상이다.
[상태/연산자 비교 원칙](../USER_PRIMARY_HSWM_STATE_LOCAL_OPERATOR_HYPERON_2026-09-14.md)의
고정 원전·판본·성숙도 구분을 이어받는다. 이 통합본에서 새 외부 비교 실험이나 최신성
조사를 수행한 것은 아니다. 독창성·성능을 주장할 때는 해당 시점의 실제 구성과 대조한다.

### 13조의 이유·문제·구현

- **이유와 해결할 문제:** 스키마 검사 통과를 지능 개선으로, 성공한 한 사례를 일반 성능으로,
  외부 논문의 결과를 HSWM 측정으로 바꾸면 무엇이 실제로 작동하는지 알 수 없다.
  평가기와 실행기가 같은 잘못된 가정을 공유하는 경우도 별도로 발견해야 한다.
- **외부 근거:** Liang 등의 **HELM**, TMLR 2023,
  [arXiv:2211.09110v2 §2·§4](https://arxiv.org/html/2211.09110v2)은 시나리오·적응 방식·다양한
  지표를 명시해 평가의 범위와 절충을 드러낸다. W3C의
  [SHACL Recommendation, 2017-07-20](https://www.w3.org/TR/2017/REC-shacl-20170720/)은
  데이터 그래프가 선언된 shape 조건을 충족하는지 검사한다. 따라서 SHACL 통과가
  세계에 관한 사실성·과제 효능을 보증하지 않는다는 구분이 필요하다.
- **구현 방법:** 주장마다 대상 판본·과제·관측 범위와 근거 종류를 연결한다. 구조·권한
  오류는 schema/SHACL과 단위 테스트로, 실행 연결은 실제 I/O·admission·다음 사용으로,
  효능은 같은 과제·예산·관측 조건의 비교로 평가한다. 품질·오류·비용·지연을 함께 보고하고,
  평가기가 정답을 미리 받거나 자기 출력을 그대로 채점하는 경로를 별도 검사한다.
- **현재와 확인 방법:** 기존 HSWM_LIKENESS 평가 계약을 사용한다. 문서 수정마다 새로운
  종합 실험을 요구하지 않는다. 구조 변경에는 영향받는 구조 검사를, 효능 주장에는 해당
  비교 실험을 선택한다. 실패·무개선·미확인과 실행하지 않은 항목을 그대로 남기고,
  같은 데이터의 반복 사용이나 평가 누출로 개선 수치를 부풀리지 않는다.

## 14. 현재 실행 경로와 남은 통합 의무

| 경로 | 인정할 범위 | 남은 질문 |
| --- | --- | --- |
| 내용 지도 → 이웃 → 다른 번들 → 원문 | 이번 `navigate/follow/read` 구현과 실제 CLI 검사 | 자연어 질문의 자동 경로 선택·필요 집합의 충분성은 별도 평가 |
| native 상태 → 선택 문맥 → LLM 전이 | 기존 semantic runtime·문맥 실행 경로 | 내용 탐색 결과와 실행 read-set의 의미적 대응·최소성 |
| 실제 결과 → 정책/관계 수정 → 재개방 | 기존 활성화 학습·semantic lifecycle와 `executeActivationLoop`의 자동 연결 | 자연 과제의 정책 효능·일반 의미 위상 변화 |
| 방문 지점 → 국소 선택·학습 → 다음 지점 | `executeActivationTraversal`과 10월 24일 다단계 연결 | 자연어에서 경로를 구성하는 일반성·전체 경로의 인과 기여·복구 시 읽기 국소성 |
| 세계·자기모델 → 미래 분기 → 실제 관측 | 기존 구현 구조·FCL-6 연구 계약 | 자연 환경의 지속 동기화·장기 예측·자기개선 |
| 하위 HSWM → 합성 → 분리·재사용 | 기존 fractal/CR/FCL 문서·한정된 형식 근거 | 여러 규모에서의 손실·유지·관측 가능한 인지 효용 |

내용 지도는 현재 workspace에 등록된 기존 주제들을 주제별 작은 번들에 연결한다.
이는 등록된 범위의 탐색 coverage이며 모든 저장소 파일·모든 연구가 이해되었다는 보증이 아니다.
역사 형식이 native v2와 다르면 `SOURCE_ONLY` 지위를 보존하고 `show/bindings`로 확인한다.
내용 graph의 관계 상태 `PROPOSED`도 그대로 표시한다.

통합 확장의 판정 과제는 명확하다. 새 질문에서 여러 지도를 거쳐 선택한 실제 원문·역할을
native 실행 read-set에 결속하고, 독립 결과가 활성화/관계 판본을 바꾼 뒤, 새 프로세스가
그 판본을 사용했는지 검증한다. 고정 경로 기준선과 같은 관측만 추가한 통제를 비교하며,
필수 예외 누락·잘못된 분기·순환·낡은 원문·중복 피드백·재시작을 반례로 사용한다.
현재의 제한된 연결 근거는 [10월 24일 다단계 연결](../../operations/HSWM_MULTIHOP_ACTIVATION_2026-10-24.md)을
따른다. 이 문서 보강으로 새로운 통합 실험이나 일반 효능 검증을 완료했다고 표시하지 않는다.

### 14조의 이유·문제·구현

- **이유와 해결할 문제:** 검색기·실행기·평가기·저장기가 각각 성공해도 서로 다른 객체나
  판본을 주고받으면 한 AI의 경험으로 이어지지 않는다. 반대로 이미 연결된 자동 학습을
  미구현으로 분류하면 같은 장치를 계속 다시 만드는 문제가 생긴다.
- **외부 근거:** [ReAct §2](https://arxiv.org/html/2210.03629v3)의 행동–관측 연결과
  [MemGPT §2](https://arxiv.org/html/2310.08560v2)의 문맥–지속 기억 간 이동은 각각 경계
  연결의 설계 사례다. 두 논문 모두 HSWM 전체 통합이나 현재 저장소의 실행 결과를 입증하지 않는다.
- **구현 방법:** 위 표의 실제 연결 경계를 따라 질문·선택한 원문·역할·read-set·실행·
  outcome·정책 revision의 식별자를 이어 간다. 기존 runtime/API를 조합하고, 관측된 누락
  경계에만 어댑터를 추가한다. 입력부터 다음 사용까지 한 경로를 먼저 완성한 뒤 과제·규모를
  넓힌다. 복구가 전체 상태를 읽는다면 추론의 국소 선택과 복구 비용을 따로 기록한다.
- **현재와 확인 방법:** 목록·호출 횟수 대신 실제 전달된 문맥과 다음 선택이 소비한 판본을
  확인한다. 연결 변경 시 필요한 통합 테스트를 실행하고, 일반 사용은 기존 자동 경로를
  그대로 사용한다. 자연어 경로 구성, 경로 전체 성과의 기여 판정, 광범위 위상 재편은
  각각의 미해결 질문으로 남기며 하나의 성공 trace로 일괄 완료 처리하지 않는다.

## 15. 개정과 다음 사용

1. 원문·판본·권위와 바꿀 의미를 먼저 식별한다. 새 해석을 사용자 직접 발화로 소급하지 않는다.
2. 영향을 받는 조항·국소 지도·실행 계약을 수정한다. 공통 진입점에 모든 세부를 모으지 않는다.
3. 현재 source binding이 바뀌면 해당 현재 번들과 명시적 연결 pin을 함께 검토한다.
   과거 번들의 hash를 새 파일에 맞춰 조용히 교체하지 않는다.
4. 영향받는 질문의 실제 탐색·원문 복귀와 오류 동작을 확인한다. runtime을 바꿨으면 해당
   execution/admission/reopen 경계도 검사한다.
5. 다음 실행이 새 판본을 읽는지 확인하고 마지막 확인 단계를 보고한다. 새 문서와 테스트
   통과를 학습·효능으로 바꾸지 않는다.

재현 명령은 기존 runtime의 `npm run check`, workspace 관련 Vitest와 CLI 도움말에 있다.
한 번의 변화에 별도 보고서·점수표·원장을 계속 증식시키지 않는다. 원문·내용·코드·검사와
Git 이력이 이 작업의 지속 자료다.

### 15조의 이유·문제·구현

- **이유와 해결할 문제:** 원문 파일이 바뀌었는데 연결 hash가 그대로이면 옛 판단을 새
  문장으로 재해석하게 된다. 반대로 과거 번들의 hash를 새 내용에 맞추면 당시 무엇을
  읽었는지 사라진다. AI의 설계 보강이 사용자 직접 발화로 승격되는 문제도 막아야 한다.
- **외부 근거:** W3C **PROV-O**, Recommendation 2013-04-30,
  [derivation·revision 관계](https://www.w3.org/TR/2013/REC-prov-o-20130430/)는 판본과
  그 생성 활동·작성자·유래를 연결하는 모델을 제공한다. hash 고정, Git 보존, 현재 판본을
  가리키는 registry는 이를 HSWM 저장소에서 실현하는 공학적 선택이다.
- **구현 방법:** 사용자 원문과 AI 보강을 구분한 채 문서를 개정한다. 새 내용에 대한 현재
  번들을 새 판본으로 만들고 실제 파일 hash를 결속한다. registry와 다른 번들의 명시적
  이동 pin을 함께 갱신하되 이전 번들은 보존한다. 과거 문서는 해당 Git 판본에서 읽는다.
  현재 판본으로 재개정할 때도 원문 UID·역할·권위의 의미를 임의로 바꾸지 않는다.
- **현재와 확인 방법:** `navigate → follow → read`로 바뀐 조항에 실제 도달하고 내용·hash가
  일치하는지 검사한다. 오래된 pin·원문 drift·모호한 UID·누락 경로는 명시적으로 실패해야
  한다. 문서·binding 개정은 학습 정책 revision과 다른 사건이며, 수정 규모에 맞는 검사와
  Git 변경만 남긴다.

문헌 확인일: 2026-10-24. 이 보강은 `SECONDARY_AI` 문헌·구현 해석이며, 새 성능 점수나
사용자 원문 변경·외부 표준 준수 인증을 만들지 않는다.
