## Evidence-branch process-topology decision

### Why the long-lived root is selected

GitHub documents that ordinary steps run in separate processes while sharing
the runner workspace and filesystem. Its current workflow syntax also provides
background steps that remain active while later steps run, followed by explicit
`wait`, `wait-all`, or `cancel`. This makes a long-lived root compatible in
principle with v16's separately pinned action:

```text
background Effect root prepares fixed files and announces READY
  -> foreground exact pinned upload-artifact action
  -> always-run authenticated RECONCILE command
  -> root independently lists/requeries/downloads/validates
  -> explicit wait propagates the root result; cancel cleans incomplete paths
```

Primary references, checked 2026-08-23:

- https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax
- https://docs.github.com/en/actions/reference/runners/github-hosted-runners
- https://github.com/actions/upload-artifact

The documentation is design evidence only. No hosted run in this repository
has demonstrated the topology.

### Frozen ownership and IPC boundary

- One structured `Effect.scoped` root owns current-run acquisition,
  predecessor replay, preparation, the authentic prepared capability, the
  assertion Layer, completion, and replay until terminal cleanup.
- The root materializes only the fixed upload files, snapshots their hashes,
  and verifies them immediately before and after the pinned action.
- IPC is a root-private one-shot Unix-domain socket under a newly created
  `0700` directory in `RUNNER_TEMP`; the socket and token material are no more
  permissive than `0600`.
- A root-generated random nonce binds protocol version, root PID, run attempt,
  stage, and job identity. READY, RECONCILE, and terminal status transitions
  are monotonic and replay-rejecting.
- IPC carries no bearer, permit, artifact selector, artifact ID, digest, member
  roster, observer, transport, codec mode, or postcondition.
- `steps.upload.outcome` and action outputs are untrusted diagnostics/control
  input. The root reconciles independently even after an action failure whose
  publication outcome may be unknown. It never blindly retries an upload.
- `SIGINT`/`SIGTERM` interrupt the structured root and run bounded infallible
  finalization. `SIGKILL`, root death, or missing terminal authentication emits
  no completion and never replenishes authority.
- No child or daemon may outlive the job/root scope.

### Why deterministic reacquisition is deferred

Fresh preregistration, invocation, current-run, prepared-carrier, and replay
issuers exist, and the file substrate has create-only hard-link CAS. Those
pieces are insufficient for authenticated post-action reacquisition:

- the caller-selected durable path has no independent root provenance;
- content hashes authenticate bytes, not the writer principal;
- the complete current-stage archive/postcondition attachment CAS is absent;
- the new process has no independent source for expected current-stage bytes
  unless it recomputes them bit-for-bit or trusts a separate signer; and
- crash/AlreadyCommitted/restart rules do not yet prevent authority
  replenishment across workers.

Reconsider this candidate only if an authenticated shared root, complete-stage
CAS/recovery, independent byte reconstruction, and hostile cross-worker replay
tests are established. Determinism alone never authenticates a bearer.
