## Exact scientific question and construction

The question is whether, under source/runtime-trusted repeated-context
exhaustive forced exposure, a fixed scorer-outcome-bound integer routing
payload:

- persists across fresh-process recovery;
- changes pre-model route selection relative to exact W0 rollback;
- loses that alignment when context bindings are deranged; and
- is reproduced by fixed-rule replay of the same retained training update
  records.

The construction remains intentionally small and unchanged in its causal arms:

- Four future-seeded streams each contain four context keys and two routes.
- Training forces all eight context-by-route cells exactly once per stream.
- Heldout evaluation reuses the same four contexts; this is not unseen-context
  generalization.
- `FULL` applies eight locally declared scorer outcomes per stream to the
  durable numeric field, for 32 training generation requests in total.
- `NO_MEMORY_ROLLBACK` recovers exact immutable W0.
- `RAW_EQUAL_BUDGET` replays the same eight retained update records per stream
  through the same fixed integer rule from W0. It is a replay-fidelity control,
  not a model-visible transcript or equal-token comparison.
- `BINDING_DERANGED_NUMERIC_PLACEBO` preserves the matched numeric payload byte
  count, precision, update multiset, and norms while permuting context bindings
  within stratum. It does not claim full atom, history, or reference parity.
- The maximum is 32 training plus 128 evaluation generation requests. There are
  no retries. Provider-side physical work, cache independence, and determinism
  remain unobservable.

The model receives preselected evidence and is asked to return its response
token. Positive routing separation is therefore substantially
construction-driven. The model is a response boundary, not the learner whose
generalization is under test.

## Response-boundary decision

Every generated response token is source-constrained to the ASCII pattern
`token-[0-9a-f]{20}` and exactly 26 UTF-8 bytes. DNRD-2 raises the completion
ceiling from 16 to 64 tokens. This is operational headroom, not proof that every
possible completion will stop normally. The deployment preflight makes one
source-frozen non-generation probe, `token-ffffffffffffffffffff`, and the experiment does **not** claim that
this representative probe proves tokenization of the complete future-seeded
response family or the provider's stopping behavior.

The actual admissibility condition is observational and per call: HTTP success,
the pinned served-model identifier, exactly one choice, exact
`finish_reason="stop"`, one non-whitespace textual response token, and coherent
nonnegative usage arithmetic. A failure is retained as an inconclusive
singleton and cannot be retried.

An alternative design would add 128 future-seeded `/tokenize` calls. That would
verify tokenizer counts for those exact strings but still would not prove chat
template behavior or `stop`; it also would not test HSWM learning. DNRD-2 does
not add that harness surface. This limitation is explicit rather than hidden.

## Rejected-response and bundle evidence

The live-event schema is versioned for DNRD-2. For an exact bounded HTTP
response rejected by the parser or status gate, the occurrence retains:

- response byte length, SHA-256, and exact base64 bytes;
- exact HTTP status and call/request identities;
- a stable failure-stage code; and
- a safe exact failure message plus its SHA-256.

Request headers, authorization values, and environment credentials are never
serialized. The occurrence directory is owner-only external evidence and raw
responses are not checked into the repository. Base64 is an exact encoding,
not encryption. The production transport and answerer both impose a 1 MiB body
ceiling. If that ceiling is crossed, the event retains and independently binds
the exact first 1,048,577 bytes as a prefix and lower bound; it does not claim
the digest or total length of the unconsumed remainder. An invalid transport
object is recorded separately and cannot be misrepresented as a real zero-byte
HTTP response.

The independent judge must replay accepted and rejected partial live-event
pairs, raw-body commitments, ordinals, configuration, and the inconclusive
failure digest. Every accepted prior model call must have exactly one
shape-checked runner row whose full request identity and provider-body digest
reproduce that call. The runner row's downstream semantic contents, terminal
rejected-call request preimage, and retained common context are not replayed as
a completed candidate. A nonempty declared call count with an empty, tampered,
reordered, duplicated, or contradictory model-boundary ledger cannot receive
verified inconclusive authority. In the production path, each live-model event
is appended to an owner-only JSONL ledger and fsynced before control proceeds.
A process or storage failure can still leave only a partial, unindexed forensic
ledger; that is not a verified occurrence and cannot be resumed or retried.

The bundle producer orders canonical artifacts by serialized relative POSIX
path, not component-wise `Path` ordering. The judge independently rehashes and
checks the index, rejects symlinks and extra/unindexed artifacts, and emits
unverified `VOID_PROTOCOL` wording if structural verification fails. This does
not eliminate same-UID TOCTOU risk, provide hostile-host attestation, or seal
file modes as scientific observations.
