G1 local causal revision.  The current opaque-action occurrence established an
exploratory local state-readout signature, but its same-process evaluator did

## 5. Future-outcome component

The implemented component binds exactly twenty ordered opaque two-action
episodes because it reuses the already pinned twenty-seed Quicknet verifier.
Before a live run, its registration payload fixes:

- exact Quicknet chain, round, and round time;
- exact ordered episode and action-code roster;
- analysis, final-holdout, and arm-schedule SHA-256 values; and
- one registration payload digest that must equal the future-round
  commitment's `registration_evidence_sha256`.

Every planned actor action must then appear exactly once in a caller-declared
pre-pulse seal.  Missing or duplicate episode entries, foreign action codes,
post-pulse caller timestamps, changed analysis, changed holdout, changed arm
schedule, or use of a different commitment fail closed.  The module does not
provide a durable occurrence registry and therefore cannot itself prevent a
caller from executing the same seal again or selecting among several registered
rounds.  After the exact pulse is BLS verified, a domain-separated SHA-256
projection maps each bound seed to one of the two bound actions.

This is synthetic outcome instrumentation only.  Its receipt always enforces:

```text
action chronology independently established = false
outcome owner independence established       = false
CF-07 satisfied                               = false
G0 pass allowed                               = false
independent replay required                   = true
registration timestamp independently established  = false
external singleton/no-retry registry implemented  = false
verifier execution evidence embedded              = false
receipt alone proves verifier execution            = false
```

The online entry point executes the pinned verifier.  The offline entry point
accepts only a caller-supplied, bounded historical pulse fixture that the same
pinned BLS verifier accepts against the exact commitment; it remains a known-answer or
metamorphic qualification path, never a live occurrence.  A stored receipt or
derived seed bundle cannot stand in for a new BLS execution or an independent
replay.  The in-process capability passed
from the verifier call to the projection is an API guard, not an attestation or
a hostile-process security boundary.  A later occurrence therefore still
needs a content-addressed raw verifier bundle and an independent replayer.

A new prospective occurrence may be sealed only after all of the following
exist:

6. the final holdout is lineage-disjoint and has a fixed inspection budget;
7. one source-pinned reuse-first comparator, currently the qualified ExpeL B2

   owner/`Permit` admission path and exact remove/byte-identical restore.
